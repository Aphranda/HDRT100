## 0. 导读

### 0.1 一句话

用**单一事实源 + 契约 + 可恢复工作流 + 可复跑证据**，把大型项目从"靠人的记忆和聊天记录驱动"，变成"靠系统状态和证据驱动"；让 AI 能在受控边界内自主执行，让人只对不可逆决策负责。

### 0.2 这套体系解决什么问题

大型项目最常见的失败，不是某个人能力不够，而是：

1. **事实分裂**：同一件事在会议纪要、聊天、文档、代码里有四个版本，没人知道哪个是真的。
2. **状态失忆**：三个月后没人说得清"当时为什么这么定、现在做到哪、下一步是什么"。
3. **验收失真**：口头说"测过了"，但换一台机器、换一个版本就复现不了。
4. **AI 失控**：让 AI 写代码/文档，它改了什么、依据是什么、失败后怎么恢复，都没有记录。
5. **协作污染**：多个 agent 同时写同一批文件，互相覆盖，最后没人敢合并。
6. **治理反噬**：规则越加越多、门禁越来越慢，大家开始绕过，体系名存实亡。

本规范用六个系统、两个闭环、四条分离来系统性解决这些问题。

### 0.3 三条主线

| 主线 | 回答的问题 | 对应系统 |
|---|---|---|
| 事实线 | 什么是真的？谁定义的？ | 文档体系、契约体系 |
| 执行线 | 谁来做？怎么做？失败了怎么办？ | 工具体系、技能体系、工作流体系 |
| 信任线 | 凭什么相信做完了？谁复核？ | 证据与验收体系、协作与评审体系 |

### 0.4 两个闭环

**变更闭环**（一次改动的完整生命周期）：

```text
需求/问题 → 契约冻结 → 文档更新 → 实现/配置 → 验证 → 证据 → 提交 → 索引与状态刷新
```

**认知闭环**（长期任务不跑偏）：

```text
里程碑 → 复议上轮"下一步" → 偏差与残余 → 新证据 → 下一里程碑
```

变更闭环保证"做得对"，认知闭环保证"一直在做对的事"。

### 0.5 四条分离

1. **语义 / 状态 / 证据分离**：架构文档只写稳定语义，TODO 只写状态，进度日志只写证据；三者不互相冒充。
2. **分析 / 执行分离**：只读复核者只取证、不写文件；写操作和不可逆操作由主控在复核后执行。
3. **代码 / 文档提交分离**：代码变更与文档/契约变更分开提交，历史可审计。
4. **生成 / 验收分离**：做的人不给自己发合格证；验收由独立凭证和独立复核完成。

### 0.6 如何阅读

- **项目负责人/决策者**：读 §1、§9、§10、§11，先判断"要不要做、做到什么程度"。
- **体系搭建者/技术负责人**：读 §2–§8，按 §10 的路线图落地。
- **一线工程师/AI 工作流使用者**：读 §2.3、§5、§6、§7 和附录模板。
- **结构专业同事**：先读 §10.4 的领域映射，再回到通用章节取模板。

### 0.7 不适用场景

- 一次性、无交付物、无协作的个人脚本；
- 生命周期短于两周且不需要复现的实验；
- 没有明确 owner、也不准备指定 owner 的"临时项目"。

治理是有成本的。**当治理成本大于它减少的返工时，应该裁剪，而不是硬套。**

## 1. 体系总览

### 1.1 目标与成功判据

体系的目标不是"文档多、流程全"，而是四个可观察的结果：

| 判据 | 可观察指标 | 目标 |
|---|---|---|
| 可发现 | 新人/新 AI 在 30 分钟内找到当前事实、owner、下一步 | 不需要问人 |
| 可恢复 | 任意一次交付能按记录复跑，或明确说明为什么不能复跑 | 证据路径可执行 |
| 可交接 | 换人/换会话后，工作不从零开始 | 交接包完整 |
| 可审计 | 每个"完成"都能追到契约、改动、凭证、复核人 | 链路闭合 |

### 1.2 十条设计原则

| # | 原则 | 含义 | 典型反模式 |
|---|---|---|---|
| P1 | 单一事实源 | 同一事实只存一处，其他位置只引用 | 登记表、文档、代码各写一份数字 |
| P2 | 契约先行 | 跨边界的稳定承诺先冻结、再实现 | 先写代码，接口靠口头约定 |
| P3 | 文档即代码 | 元数据、命名、索引、新鲜度可机器检查 | "文档写完了"但没人知道在哪 |
| P4 | 证据优先于叙述 | 结论必须能追到原始证据；快照必须标注 | "应该没问题""上次测过" |
| P5 | 门禁可机检、可绕过但留痕 | 自动检查优先；逃生门必须被记录和审计 | 门禁靠自觉，绕过无人知道 |
| P6 | 归档不删除 | 历史只归档、不物理删除；契约只失效、不删行 | 为了"干净"删掉旧证据 |
| P7 | 分析与执行分离 | 复核者只读；写操作由主控执行 | 作者自审自批 |
| P8 | 小步闭环、批量受控 | 每次改动有边界、有证据、可回退 | 一次改 80 个文件再验收 |
| P9 | 工具先判型 | 新脚本先判断是工作流/步骤/独立工具/库 | 根目录堆满一次性脚本 |
| P10 | 技能指针化 | Skill 指向权威，不复制规则 | 同一规则在 4 个地方各写一遍 |

### 1.3 体系结构

```text
                     ┌──────────────────────────────────────────┐
                     │              治理与角色                    │
                     │  决策权 · 写域 · 独立复核 · 里程碑 · 审计   │
                     └───────────────────┬──────────────────────┘
                                         │
          ┌──────────────────────────────┼──────────────────────────────┐
          │                              │                              │
   ┌──────▼──────┐                ┌──────▼──────┐                ┌──────▼──────┐
   │   事实层     │                │   执行层     │                │   信任层     │
   │ 文档体系     │                │ 工具体系     │                │ 证据与验收   │
   │ 契约体系     │                │ 技能体系     │                │ 独立复核     │
   │ 索引/元数据  │                │ 工作流体系   │                │ 里程碑报告   │
   └──────┬──────┘                └──────┬──────┘                └──────┬──────┘
          │                              │                              │
          └──────────── 变更闭环 ─────────┴───────── 认知闭环 ──────────┘
```

### 1.4 六个系统的职责边界

| 系统 | 回答的问题 | 唯一事实源 | 明确不负责 |
|---|---|---|---|
| 文档体系 | 事实在哪、是否新鲜、如何查找 | 文档本身 + 总索引 | 不定义业务规则，不替代契约 |
| 契约体系 | 跨边界承诺是什么、谁批准、是否生效 | 契约登记表 | 不记录实施细节和单次结果 |
| 工具体系 | 有哪些可执行能力、谁维护、能否依赖 | 工具登记表 + 判型表 | 不定义业务语义和验收资格 |
| 技能体系 | AI 遇到什么场景、按什么步骤做 | Skill 文件 | 不复制权威规则，不替代文档 |
| 工作流体系 | 多步操作如何编排、失败如何恢复 | WorkflowSpec + 运行状态 | 不定义新命令语义，不替代验收判定 |
| 证据与验收体系 | 凭什么相信做完了、能否复跑 | 凭证 + 原始证据 + 独立复核 | 不定义业务语义，不替代产品判断 |

### 1.5 权威顺序

发生冲突时，按以下顺序取权威，低优先级不得覆盖高优先级：

```text
1. 系统安全要求、法律法规、用户当前明确指令
2. 项目章程 / AGENTS.md / 治理硬约束
3. 契约登记表 / 运行时约束（冻结的跨域承诺）
4. 域 canonical 文档（架构、接口、约束）
5. Skill / 操作手册 / 检查清单
6. 会议纪要、聊天记录、个人笔记
```

Skill 如果与上层冲突，**Skill 必须被修正**，而不是"按 Skill 执行"。权威顺序必须在项目入口文档里写明，否则 AI 会随机选一个。

### 1.6 成熟度模型

| 级别 | 名称 | 特征 | 典型团队 |
|---|---|---|---|
| L0 | 人治 | 事实在脑子里，验收靠口头 | 起步期 |
| L1 | 有文档 | 有文档和目录，但无强制、无新鲜度 | 3–10 人 |
| L2 | 有门禁 | 元数据/索引/契约/工具登记可机检，提交前拦截 | 10–50 人 |
| L3 | 有证据 | 每个改动有凭证、指纹、scope；失败可复跑 | 20–200 人 |
| L4 | 自回归 | 检查器自身有测试；治理规则定期审计和简化 | 长期平台型团队 |

大多数团队不需要一步到 L4。**先到 L2，再选一个高价值链路做到 L3**，比全量铺开更有效。

## 2. 文档管理体系

### 2.1 文档不是知识库，是事实源

知识库追求"多"，事实源追求"准"。项目文档的第一职责不是保存所有信息，而是让读者在需要时**找到唯一可信的答案**。

按职责把文档分为四类，禁止一类文档承担多种职责：

| 类型 | 回答的问题 | 典型文件 | 生命周期 |
|---|---|---|---|
| 稳定语义 | 系统为什么这样设计、边界在哪 | 架构、接口、约束 | 长，变更需评审 |
| 计划状态 | 做到哪、下一步是什么 | TODO、里程碑表 | 中，随进展更新 |
| 执行证据 | 哪次构建、哪次验证、失败是什么 | 进度日志、验收记录 | 只追加，可归档 |
| 决策与评审 | 当时有哪些方案、为什么选它 | 评审单、决策记录 | 冻结快照，不冒充事实 |

### 2.2 域文档"三件套"

每个有架构、有实施、有证据的域，至少维护三份文档：

| 文件 | 唯一职责 | 必须写 | 禁止写 |
|---|---|---|---|
| `*_ARCHITECTURE.md` | 稳定语义、owner、不变量、契约落点 | 边界、数据/状态模型、失败与恢复、验证映射 | 单次构建号、板端日志、临时完成判断 |
| `*_TODO.md` | 里程碑、任务状态、进入/退出门禁 | 稳定 task ID、状态、完成定义、证据索引 | 复制单次快照、把一次性结果写成架构事实 |
| `*_TASK_PROGRESS.md` | 提交、构建、验证、失败、回退 | 日期、任务 ID、改动、命令、结果、证据路径 | 冻结新契约、替代 TODO 状态、改写旧失败 |

三件套之间必须互相引用，但**不得互相复制**。语义变更先改架构并登记契约；状态变更改 TODO；实施证据只追加到进度日志。

最小结构：

```text
Architecture: 文档接口 / 范围与边界 / owner 与不变量 / 数据或状态模型 /
              跨域契约 / 失败与恢复 / 验证映射
TODO:         文档接口 / 状态规则 / 已有基线 / 当前主线 / 里程碑总览 /
              分阶段任务表 / 当前阻塞 / 完成定义
Task Progress: 文档接口 / 当前 checkpoint / 按时间追加的记录 /
              验证与证据索引 / 失败与回退 / 下一 gate
```

### 2.3 元数据与状态

每份受治文档在标题后 7 行内写 5 个字段，顺序固定，不多不少：

```markdown
# 文档标题

Status: Active
Domain: <域>
Canonical: `<仓库相对路径>`
Related: `<路径1>`, `<路径2>`
Last updated: YYYY-MM-DD
```

规则：

- `Status` 枚举：`Draft` / `Active` / `Frozen` / `Deprecated`。不发明近义词。
- `Canonical` 必须是本文档自身路径；一个主题只有一个 canonical。
- `Related` 只放真正相关的入口，不堆砌。
- `Last updated` 每次实质修改都更新；必须是合法日历日期。
- 额外字段（Target、Source of truth 等）放在 5 个必填字段之后，避免挤掉窗口。

### 2.4 命名与目录

文件名格式：

```text
<DOMAIN>_<SUBJECT>_<TYPE>.md
```

- `DOMAIN`：全大写 ASCII 域前缀，如 `ARCH`、`TOOLS`、`STRUCT`。
- `SUBJECT`：全大写 ASCII 主题，下划线分隔。
- `TYPE`：从白名单选择，如 `_ARCHITECTURE`、`_DESIGN`、`_PLAN`、`_TODO`、`_TASK_PROGRESS`、`_CHECKLIST`、`_PLAYBOOK`、`_CONSTRAINTS`、`_ANALYSIS`。
- 新文档不用中文文件名、日期、`final`、`new`、`v2`；版本用元数据/内容管理。
- 一个文档只承担一种主职责；不把 TODO 和进度日志混在一份文件里。

目录按"域 + 职责"组织，不按文件类型机械分层：

```text
docs/
  README.md                 总索引与域路由
  <domain>/
    README.md               域入口
    <DOMAIN>_ARCHITECTURE.md
    <DOMAIN>_TODO.md
    <DOMAIN>_TASK_PROGRESS.md
    <DOMAIN>_<TOPIC>_<TYPE>.md
  legacy/<domain>/          归档，不删除
```

### 2.5 索引与路由

索引不是"目录截图"，而是**导航 contract**：

1. 总索引必须列出所有受治文档，至少包含路径、定位、owner/域。
2. 每个域必须有入口 README，说明"先读什么、再看什么"。
3. canonical 表要能直接回答"这个主题的权威文档是哪份"。
4. 进度日志要有路由表：哪类任务写到哪个文件。
5. 新增、改名、移动、归档文档，必须在同一次变更里更新索引。

跨域索引（总 README、契约登记表、提交单索引）只允许**一个写者**（主控/文档 owner）。两个 agent 同时写同一个索引，必然出现"file changed since it was read"。

### 2.6 新鲜度

文档的新鲜度是缺陷，不是风格问题。

- 任何实质修改都更新 `Last updated`。
- 新契约登记后，顶层架构/总览文档在**窗口期**内刷新；建议窗口 7 天，按项目节奏调整。
- 顶层文档引用的契约、代码锚点、指标，必须在窗口内保持一致。
- 过期未刷新的文档，检查器应报 WARN 或 FAIL，而不是静默放过。

### 2.7 硬数字与快照

文档里最容易腐烂的是数字。规则：

1. **能引用符号就不写数字**：引用代码常量、配置项、登记表条目。
2. **必须写数字时，登记为契约或事实源**：写清单位、口径、生效版本。
3. **临时测量值必须标注**：`快照，非事实源`，并写日期、环境、构建号。
4. **禁止**在架构文档里写"当前 37 步""现在 813 条命令"这类会漂移的数字，除非它来自可检查的源。

### 2.8 进度日志

进度日志是只追加的证据日志，必须**可读、有界、可检索**。

条目格式：

```markdown
### <PREFIX>-YYYYMMDD-NNN：<一句话标题>

- **任务**：<TODO task ID>
- **变更/提交**：<改了什么，commit 号>
- **构建/验证**：<命令、build 号、环境>
- **结果**：PASS / FAIL / BLOCKED / PARTIAL
- **证据**：<out/... 路径、日志、截图、凭证>
- **失败/回退**：<原始错误、是否回退、回退到哪个版本>
- **下一步**：<下一 gate 或阻塞点>
```

规则：

- 条目 ID 稳定且唯一；`YYYYMMDD` 是合法日期，`NNN` 是当日序号。
- 按新鲜度**倒排**：最新在顶部；新条目写在"当前 checkpoint"之后。
- 单文件上限建议 200 KB；超过后把**最旧**的连续一段归档到 `legacy/<domain>/`，保留索引闭包。
- 归档只搬旧证据，不改写、不删除；归档索引记录文件、ID 区间、条目数、日期。
- 失败必须保留原始错误和回退结果，不能被"最终通过"摘要覆盖。

### 2.9 评审快照与草稿

评审快照、方案草稿、会议结论**不是契约**，不得登记为契约。规则：

- 用 `Status: Draft` 或 `Status: Frozen` 明确标注。
- 放在 `temp/`、`reviews/` 或 `submissions/`，不要放进 canonical 表。
- 快照可以引用契约，但不能成为契约的替代事实源。
- 评审结论要写"审核对象、审核方、证据、结论、必改项、复审状态"。

### 2.10 归档与迁移

- 历史文档、旧实现、旧配置只归档，不删除。
- 归档目录明确标注 `legacy/` 或 `archive/`，默认只读。
- 迁移不搞大爆炸：先建新入口，再小批量迁移，每批更新索引、链接、调用方、测试。
- 旧路径需要兼容时，保留转发入口；确认无调用者后再退役。
- 归档资料不得作为默认构建、验收或运行时输入；需要恢复时走显式恢复提案。

### 2.11 文档门禁

文档门禁必须**只读、快速、可解释**。最低检查集：

| 检查 | 判据 | 失败动作 |
|---|---|---|
| 元数据 | 5 字段齐全、顺序正确、日期合法 | FAIL，阻断提交 |
| 索引 | 每个受治 .md 在总索引有行 | FAIL |
| 命名 | 前缀/后缀在白名单，ASCII | FAIL |
| 链接 | 相对链接目标存在 | FAIL |
| 新鲜度 | 顶层文档在上次契约登记后的窗口内 | WARN/FAIL |
| 契约锚点 | `clause_loc`、`code_anchor` 真实存在 | FAIL |
| 进度轮转 | 单文件 ≤ 上限、归档连续、索引闭包 | FAIL |
| 硬数字 | 未登记的裸常量 | WARN/FAIL |

工程要求：

- 检查器只读，永不改文件。
- 检查器不导入、不执行被检查的工具，不访问硬件。
- 零依赖或极少依赖，离线可跑。
- 全套检查 ≤ 5 秒；超过 10 秒的门禁一定会被绕过。
- 检查器自身要有正反用例；改检查器必须同步改测试。
- 允许 `--no-verify` 逃生，但必须写日志；每周审计逃生记录。

### 2.12 常见失败模式

| 失败模式 | 症状 | 纠正 |
|---|---|---|
| 文档倾倒场 | 什么都往里放，没人读 | 按四类拆分，删除无 owner 文档 |
| 双源漂移 | 登记表和文档各一份 | 只留一处，其他改引用 |
| 快照当事实 | 三个月前的数字还在用 | 标注快照，定期复核 |
| 索引腐烂 | 新文件不在索引里 | 索引纳入完成定义 + 门禁 |
| 日志无限膨胀 | 单文件几 MB，没人翻 | 200 KB 上限 + 最旧归档 |
| 元数据出窗 | 额外字段挤掉必填 | 5 字段固定最前 |
| 文档比代码长 | 写了很多，决策没增加 | 用"决策密度"评估，删水词 |

## 3. 契约管理体系

### 3.1 什么是契约

契约是**跨边界、稳定、可验证**的承诺。它回答"两边按什么约定交互"，而不是"内部怎么实现"。

适合登记为契约的内容：

- 接口/协议：报文格式、字段、错误码、命令语义；
- 参数/容量：上限、步长、超时、内存/带宽预算；
- 时序/实时性：周期、截止时间、相位、优先级；
- 数据/状态：状态机、所有权、生命周期、版本兼容；
- 验收判据：什么条件下算通过、什么条件下必须拒绝。

不适合登记的内容：

- 单次构建号、某次测试结果、临时性能数字；
- 内部实现细节、个人偏好、会议结论；
- 还没冻结、还在评审中的方案（先放 Draft/评审单）。

### 3.2 契约生命周期

```text
Draft（草案，未登记）
   │ 冻结 + 交叉审核
   ▼
pending（已登记，待证据闭合）
   │ 证据齐全 + 审核通过
   ▼
active（生效）
   │ 被替代 / 废弃 / 违反
   ▼
superseded / deprecated / VIOLATED
```

规则：

- 契约一经登记，**不可物理删除**；只能转 `superseded`，保留历史行。
- `pending` 不得写成 `active`；`active` 必须有证据和审核记录。
- `VIOLATED` 是显式状态，不是"暂时忽略"。
- 版本号只在语义变化时递增；编辑措辞不升版本。
- 状态变更必须由独立于作者的审核方确认（下称"独立交叉审核"）。

### 3.3 契约登记表

唯一事实源是一张表，字段建议：

| 字段 | 含义 | 约束 |
|---|---|---|
| `contract_id` | 稳定 ID，`<DOMAIN>-<TOPIC>-<NN>` | 全库唯一，不可复用 |
| `domain` | 所属域 | 与文档域一致 |
| `contract` | 一句话说清承诺 | 可判定，不写"做好" |
| `ver` | 语义版本 | 整数递增 |
| `clause_loc` | 契约正文所在文档/锚点 | 文件必须存在，Status 为 Active/Frozen |
| `code_anchor` | 代码落点（文件/符号） | 必须真实存在 |
| `check` | 如何验证 | 可执行命令/用例/审查项 |
| `registered` | 登记日期 | 合法日期 |
| `status` | 状态 | pending/active/superseded/VIOLATED |

示例：

```markdown
| STRUCT-IF-03 | struct | 结构与机电接口坐标统一采用项目基准点，偏差 ≤ 2 mm | 1 | STRUCT_INTERFACE_ARCHITECTURE.md:IF-03 | struct_interface.h | 基准点复核用例 + 专业会签 | 2026-11-06 | pending |
```

### 3.4 条款落点

顶层硬约束（安全、实时、兼容、发布）必须能在下层找到"落点"：

- 每条顶层条款有唯一的 `clause_id`；
- 落点行写清模块、验证方式、状态；
- 不允许孤儿条款（顶层有、下层无）；
- 评审发现违反时，状态改 `VIOLATED`，并登记整改任务。

### 3.5 独立交叉审核

契约状态变更必须由**作者之外**的审核方确认。审核方可以是人，也可以是只读 agent，但必须满足：

1. **独立取证**：自己读源码/日志/证据，不只看作者的复述。
2. **只读**：不改文件、不操作设备。
3. **可追溯**：提交单记录审核方、方式、证据位置、结论。
4. **结论明确**：`APPROVE` / `APPROVE_WITH_NOTES` / `PASS_WITH_CHANGES` / `REJECT`。
5. **必改项闭环**：`PASS_WITH_CHANGES` 必须列出必改项和复审状态。

禁止：作者自审自批、审核方只复述作者结论、用"看起来没问题"替代证据。

审核单模板：

```markdown
## 审核对象
- contract_id / 文档 / 提交：
- 作者：
- 审核方：
- 审核方式：只读代码审查 / 证据复算 / 独立用例

## 证据
- 文件:行：
- 命令与输出：
- 凭证/日志路径：

## 结论
- 结论：APPROVE / APPROVE_WITH_NOTES / PASS_WITH_CHANGES / REJECT
- 必改项：
- 复审状态：
```

### 3.6 变更影响分析

任何契约变更，登记前回答六个问题：

1. 谁消费这个契约？（下游模块/专业/工具）
2. 哪些测试、文档、配置、凭证会失效？
3. 是否需要迁移/兼容层？旧版本还能不能用？
4. 顶层文档是否需要在窗口内刷新？
5. 回滚方式是什么？回滚后旧证据是否仍有效？
6. 谁复核、用什么证据复核？

影响分析写在提交信息或评审单里，不写在契约正文里。

### 3.7 契约与快照的边界

- 只有**正式冻结**的语义才能登记。
- 评审快照、草稿、临时备注不得登记。
- 单次测量值可以写进证据/进度日志，但不能写成契约。
- 契约正文不复制实现细节；实现细节放代码/设计文档，契约只写"必须成立的性质"。

### 3.8 契约门禁

| 检查 | 判据 |
|---|---|
| ID 唯一 | 全库无重复 |
| 锚点真实 | `clause_loc` 文件存在且 Active/Frozen；`code_anchor` 存在 |
| 状态合法 | 枚举内；pending 不得冒充 active |
| 不删除 | 历史行仍在，只能 superseded |
| 草稿不登记 | Draft 文档不得作为 clause_loc |
| 条款覆盖 | 顶层条款有落点，无孤儿 |
| 审核记录 | 状态变更附交叉审核单 |

### 3.9 常见失败模式

| 失败模式 | 后果 | 纠正 |
|---|---|---|
| 契约通胀 | 什么都登记，维护不动 | 只登记跨边界、稳定、可验证的承诺 |
| 锚点造假 | 指向不存在的文件/符号 | 登记前先确认实际路径 |
| 自审自批 | 错误无人发现 | 强制独立审核，轮换审核人 |
| 只登记不验证 | 契约变成愿望 | 每条契约必须有 check |
| 版本乱跳 | 下游无法兼容 | 语义变化才升版，写兼容矩阵 |
| 删除历史 | 无法追溯 | 只 superseded，不删行 |

## 4. 工具管理体系

### 4.1 工具是资产，不是脚本堆

工具治理的目标：**任何接手者只靠仓库、依赖声明和证据，就能定位、运行、复核一个工具**，不依赖聊天记录、个人绝对路径、未登记脚本。

工具登记至少包含：

| 字段 | 含义 |
|---|---|
| `id` | 稳定 ID，`TOOL-<NAME>` |
| `purpose` | 一句话用途 |
| `domain` | 所属业务域 |
| `owner` | 维护角色（不是临时个人） |
| `lifecycle` | 生命周期状态 |
| `operation` | 离线/只读设备/配置设备/编程设备/混合 |
| `entrypoints` | 明确入口 |
| `files` | 精确文件归属（不是目录通配） |
| `depends_on` | 依赖的其他工具/库 |
| `external_dependencies` | 外部包/系统依赖 |
| `aliases` | 兼容路径 |
| `validation` | 验证证据 |
| `handoff_evidence` | 交接复现证据 |

### 4.2 四型判型

新增脚本**先判型，再使用**。四种形态：

| 形态 | 定义 | 必须具备 | 典型例子 |
|---|---|---|---|
| `WORKFLOW` | 分阶段编排，可能等待/恢复 | 入口、证据根、续跑方式、WorkflowSpec | 多板升级、验收、建模-计算-出图 |
| `STEP` | 被某个 WORKFLOW 调用 | 指向所属 WORKFLOW | 单个查询、单个编译步骤 |
| `STANDALONE` | 单次命令、单一目的 | 明确输入输出、退出码 | 格式转换、离线分析 |
| `LIBRARY` | 被 import 复用 | 不得声明独立入口 | 协议编解码、公共时钟 |

判型规则：

- 新脚本默认按 WORKFLOW 设计；确实不需要的，必须写明理由（单次命令/无阶段/无恢复/无凭证）。
- 以 `*_workflow.py` 命名的入口，必须判为 WORKFLOW。
- 存量脚本用 `target_form` + `milestone` 登记迁移目标，检查器输出 `migration pending`；完成后改 `form` 并删除迁移字段。
- 判型是使用前置条件：没有判型行，不得进入正式依赖。

### 4.3 生命周期

| 状态 | 准入 | 退出 |
|---|---|---|
| `UNASSESSED` | 已接管但未完成评估 | 完成依赖/运行条件复核 |
| `EXPERIMENTAL` | 有用途、owner、转正条件 | 依赖闭合、测试通过、交接复现 |
| `SUPPORTED` | 依赖闭合、说明完整、测试通过、交接完成 | 被替代或不再维护 |
| `DEPRECATED` | 有替代入口、调用者清单、迁移方式 | 调用者清零 |
| `ARCHIVED` | 保留历史复现价值 | 不删除，只读 |

`SUPPORTED` 不等于"产品验收通过"；工具能跑，不代表被测系统合格。

### 4.4 布局与依赖

推荐布局：

```text
tools/
  README.md                 导航（可从登记生成）
  tool_registry.json        工具身份
  tool_workflow_triage.json 判型
  domains/<domain>/<tool>/  单域工具
  common/<capability>/      跨域公共能力
  workflows/<workflow>/     跨工具编排
  build/<tool>/             构建/发布
  host/<tool>/              主机侧工具
  archive/<domain>/...      只读归档
```

规则：

- 根目录不再新增独立业务脚本；新工具进对应域。
- 一个能力只有一个 canonical 实现；其他位置用兼容包装转发。
- 依赖方向：workflow → domain tool → common；common 不反向依赖业务。
- import 不启动设备；设备访问放在显式入口。
- 正式工具不得依赖 `out/` 里的代码；`out/` 只是证据/产物。
- 不使用个人绝对路径；设备用 UID 识别，COM 口只是运行时映射。
- 归档旧实现，不删除；旧入口保留兼容转发，确认无调用者后退役。

### 4.5 只读检查器

工具治理检查器本身必须是"可信的只读裁判"：

1. 只读：只输出 stdout/JSON，不改仓库。
2. 不执行：不 import 被登记工具、不跑 `--help`、不打开设备。
3. 快速：全量检查 ≤ 5 秒；超时就拆分或缓存。
4. 确定性：同一输入同一输出；不依赖网络、时间、随机数。
5. 可解释：每条错误给出文件、字段、期望/实际。
6. 有测试：正例 + 反例；改检查器必须同步改测试。

### 4.6 工具证据与交接

每次正式运行记录：

- 工具及依赖版本；
- 源码/构建指纹；
- 完整命令、生效配置、环境变量；
- 设备身份、接线/拓扑；
- 阶段日志、原始数据、哈希；
- 成功/失败、失败原因、设备末态、清理/恢复结果；
- 下一可执行动作。

交接验收：

- 新工作区能按声明环境完成离线复算；
- 有对应硬件时能重跑并安全恢复；
- 证据包不含密钥/本机凭据；
- 最近成功记录注明适用配置和版本，不以日期新鲜替代兼容性。

### 4.7 工具门禁

| 检查 | 判据 | 失败动作 |
|---|---|---|
| 判型覆盖 | 每个非 UNASSESSED 工具族有判型行 | FAIL |
| 工作流命名 | `*_workflow.py` 必须 WORKFLOW | FAIL |
| 证据根/续跑 | WORKFLOW 必须声明 | FAIL |
| 登记完整 | ID 唯一、入口存在、文件归属精确 | FAIL |
| 布局基线 | 不新增根脚本/未分类目录 | FAIL |
| 导航同步 | 生成的 catalog 与登记一致 | FAIL |

### 4.8 常见失败模式

| 失败模式 | 后果 | 纠正 |
|---|---|---|
| 根目录脚本堆 | 没人知道哪个能用 | 判型 + 进域 + 登记 |
| 一次性脚本转正 | 无测试、无恢复 | 先补判型/证据/说明 |
| 双实现 | 行为分叉 | 一个 canonical，其他转发 |
| 依赖 `out/` | 证据变了工具就坏 | 正式代码不依赖证据区 |
| 检查器跑工具 | 副作用/设备争用 | 只读静态检查 |
| 归档即删除 | 无法复现 | 只归档，不删除 |

## 5. Skill 管理体系

### 5.1 Skill 是什么

Skill 是**给 AI 的可触发、可执行的工作方法包**。它把"遇到什么场景、先读什么、按什么步骤做、如何判断成功"固化下来，让 AI 不依赖临场发挥。

Skill 不是：

- 权威规则本身（权威在项目章程/契约/文档）；
- 文档的副本（副本一定漂移）；
- 提示词大全（越长越难维护）；
- 一次性的聊天总结。

### 5.2 结构模板

````markdown
---
name: <kebab-case-name>
description: Use when <触发场景>; covers <能力边界>.
---

# <标题>

## 0. 权威与边界
- 本 skill 不覆盖什么；冲突时以谁为准。

## 1. 何时使用 / 不使用
- 触发条件；反触发条件。

## 2. 先读
- 必读文件清单（指向权威，不复制内容）。

## 3. 步骤
1. ...
2. ...

## 4. 命令与判据
```bash
<可执行命令>
```
- 期望输出/退出码/失败判据。

## 5. 检查清单
- [ ] ...

## 6. 失败与升级
- 常见失败；何时停止；向谁升级。

## 7. 参考
- 权威文档/工具/模板链接。
````

### 5.3 设计规则

1. **一件事**：一个 skill 只解决一类任务；不要做"万能助手"。
2. **触发词具体**：`description` 写清场景、同义词、边界；AI 靠它路由。
3. **短**：正文尽量控制在 1–2 屏；长内容放引用文档。
4. **指针化**：规则、命令、模板只保留一份，skill 指过去。
5. **可执行**：给命令、期望输出、失败判据，不给空泛建议。
6. **幂等**：重复执行不产生副作用；有副作用的步骤必须显式标注。
7. **无秘密**：不写密钥、token、个人路径。
8. **相对路径**：以仓库根解析，不依赖当前目录。
9. **可验证**：skill 涉及的门禁/检查必须能跑。
10. **要评审**：skill 变更按代码评审，至少一人复核。

### 5.4 权威关系

```text
项目章程 / AGENTS.md
        >
契约登记表 / 运行时约束
        >
域 canonical 文档
        >
Skill
        >
聊天记录 / 个人笔记
```

Skill 与上层冲突时，修 skill，不修上层来迁就 skill。Skill 里应显式写"如果与 X 冲突，以 X 为准，并修本文件"。

### 5.5 生命周期与评审

| 阶段 | 准入 | 退出 |
|---|---|---|
| Draft | 有明确场景和步骤 | 试点通过 |
| Trial | 在真实任务中用过，记录成功/失败 | 稳定复用 |
| Active | 有 owner、有触发词、有检查清单 | 被替代/场景消失 |
| Deprecated | 有替代 skill | 归档 |

维护要求：

- 每个 active skill 有 owner 和复审周期（建议季度）。
- 记录使用证据：哪类任务用过、成功率、常见失败。
- 权威变更时同步 skill；如果 skill 复制了规则，必须改指针。
- 定期合并重叠 skill，删除长期不用的 skill。

### 5.6 Skill 组合与路由

- 小 skill 组合优于大 skill：一个负责路由，多个负责具体任务。
- 路由 skill 只做"判断用哪个"，不写具体步骤。
- 同一触发词只对应一个主 skill；重叠时明确优先级。
- 一次任务加载的 skill 数量要克制；加载越多，上下文越脏。

示例目录：

| Skill | 触发 | 职责 |
|---|---|---|
| `project-entry` | 任何仓库工作 | 读入口、分车道、找 owner |
| `doc-governance` | 改文档/登记契约 | 元数据、索引、门禁、轮转 |
| `tool-governance` | 新增/修改工具 | 判型、登记、生命周期 |
| `workflow-runner` | 多步设备/交付流程 | 前置检查、步骤、恢复、凭证 |
| `milestone-report` | 长期目标汇报 | 六段模板、红线、阻塞分析 |
| `roi-balance` | 决定是否继续投入 | 边际收益判断、止损 |

### 5.7 质量度量

| 维度 | 问题 | 判据 |
|---|---|---|
| 触发准确 | 该用的时候用了吗？ | 误触发/漏触发记录 |
| 任务成功 | 按 skill 做完是否通过门禁？ | 成功率、返工率 |
| 成本 | 加载/执行消耗多少上下文和时间？ | token/步骤数 |
| 维护 | 多久失效一次？ | 漂移 incident 数 |
| 复用 | 是否跨项目可用？ | 被其他项目引用次数 |

### 5.8 常见失败模式

| 失败模式 | 后果 | 纠正 |
|---|---|---|
| 规则副本 | 权威改了 skill 没改 | 改成指针 |
| 万能 skill | 触发模糊、步骤臃肿 | 拆分 + 路由 |
| 只写原则 | AI 无法执行 | 补命令/判据/模板 |
| 无 owner | 长期腐烂 | 指定 owner + 复审 |
| 过度加载 | 上下文污染 | 按需加载、精简 |

## 6. 工作流管理体系

### 6.1 什么时候必须工作流化

满足任一条，就应定义为 workflow，而不是"按钮 + 线程 + 内存状态"：

- 多步，或需要等待设备/重启/人工确认；
- 需要中断、恢复、重试或跳过；
- 跨多个资源/角色/板卡/专业；
- 写正式配置，或产生凭证；
- 依赖前置状态（停机、校准、许可、版本）。

不满足这些条件的单次命令，保留为命令卡/独立工具即可。**不要为了"统一"把一切都工作流化。**

### 6.2 WorkflowSpec

每个 workflow 至少声明：

| 字段 | 含义 |
|---|---|
| `id` / `version` | 稳定标识与版本 |
| `inputs` | 操作员输入、文件、目标、模式 |
| `preconditions` | 前置状态、版本、许可、资源 |
| `steps` | 有序步骤；每步有 id、动作、期望、超时、失败策略 |
| `transport` | 单通道/多通道/离线；必须显式 |
| `receipt_schema` | 每步证据与最终凭证的 schema |

### 6.3 步骤模型

每个 Step 至少声明：`id`、`precondition`、`action`、`expect`、`timeout/retry`、`evidence`、`on_failure`、`idempotent`。

步骤类型：

| 类型 | 用途 |
|---|---|
| `command` | 单条写操作 |
| `query` | 只读查询 + 字段断言 |
| `wait` | 轮询直到谓词成立或超时 |
| `manual` | 等待人工确认（接线、换件、签字） |
| `subworkflow` | 复用子流程 |
| `foreach` | 有界集合迭代（必须有上限和 cursor） |
| `parallel` | 仅无写冲突的只读并行，必须带 barrier |
| `evidence` | 写 receipt/摘要/哈希 |
| `compensate` | 失败/取消时的安全收尾 |

`foreach` 不是通用循环；禁止在 workflow 里执行任意代码。

### 6.4 状态机与运行语义

```text
CREATED → PRECHECK → RUNNING
                         ↔ WAITING（设备/人工）
                         ↔ PAUSED
                       → ABORTING
                       → SUCCEEDED / FAILED / CANCELLED
```

规则：

- **状态唯一事实源是 workflow state 文件**，不是 GUI 变量、线程局部变量或日志文本。
- 同一 workflow 只允许一个 runner；GUI/CLI/远程不能同时驱动同一条 workflow。
- 支持从最后成功步骤恢复；恢复前重新校验前置条件和版本，不满足则 fail-closed。
- 不允许失败后静默从第 0 步重跑。
- 取消/中止必须回到安全态（停机/中止/释放资源），并记录取消点。
- 非幂等步骤（编程、提交、签审）必须有"已执行"证据和二次确认。

### 6.5 证据与版本

- 每步输出结构化结果：状态、原始响应、reason、hash、时间。
- 最终 receipt 绑定：workflow id/version、构建/输入指纹、资源 ID、步骤结果、失败 reason。
- workflow 版本与输入/工具/协议版本不匹配时 fail-closed，不"试一下"。
- receipt 是证据，不是资格；资格由验收规则判定。

### 6.6 成熟度

| 级别 | 能力 | 建议 |
|---|---|---|
| L0 | 命令卡/宏，无状态 | 只用于探索 |
| L1 | 线性 workflow，step 恢复，receipt | **大多数团队从这里开始** |
| L2 | 多资源/parallel/barrier/transport 切换 | 有多设备/多专业时 |
| L3 | 版本矩阵、完整 HIL、正式支持 | 平台型团队 |

v1 只做线性：顺序步骤、step cursor、JSON 状态、resume/cancel、receipt；不做复杂嵌套和任意并行。

### 6.7 与其他形式的边界

| 形式 | 特点 | 适用 |
|---|---|---|
| 命令卡 | 单条命令/查询 | 调试、探索 |
| 宏 | 固定序列，无状态/证据 | 临时重复 |
| 脚本 | 命令式，难恢复/难审计 | 一次性维护 |
| Workflow | 声明式、可恢复、有门禁/证据 | 长期流程、生产运维 |
| 验收工具 | 独立判定/凭证 | 正式验收，不塞进 workflow |

### 6.8 编排模式

- **顺序**：默认；步骤间显式依赖。
- **有界迭代**：固定上限 + cursor；每轮有证据。
- **只读并行**：仅无写冲突的查询；必须 barrier 后统一汇总。
- **子流程**：复用稳定片段；父流程负责资源生命周期。
- **补偿**：失败/取消时执行安全收尾；补偿本身也要有证据。

### 6.9 反模式

1. GUI-only 状态，页面关了 workflow 就丢。
2. ad-hoc 线程 + 无 checkpoint 的"长任务"。
3. 每个页面/CLI 各写一份步骤定义。
4. 用原始命令转发冒充 workflow engine。
5. 失败后静默从第 0 步重跑。
6. 无版本匹配检查的 resume。
7. 把验收判定塞进 workflow，自己给自己发合格证。
8. 隐藏多通道/多资源，用户以为只操作了一个。

### 6.10 工作流门禁

| 检查 | 判据 |
|---|---|
| 判型 | `*_workflow.py` 必须是 WORKFLOW |
| 规格 | id/version/inputs/preconditions/steps/transport/receipt_schema 齐全 |
| 恢复 | 有 state 文件、cursor、resume 校验 |
| 证据 | 每步 evidence + 最终 receipt |
| 安全 | 取消/失败回到安全态；非幂等步骤有确认 |
| 版本 | 版本不匹配 fail-closed |

## 7. 证据与验收体系

### 7.1 证据等级

| 等级 | 内容 | 能证明什么 |
|---|---|---|
| E0 | 口头/聊天结论 | 几乎不能证明 |
| E1 | 命令输出/日志片段 | 当时执行过，但范围不清 |
| E2 | 可复跑命令 + 原始数据 + 环境 | 在本环境可复现 |
| E3 | 结构化 receipt + 指纹 + scope + 独立复核 | 可审计、可交接 |

目标不是所有改动都到 E3，而是**关键改动必须到 E3**，其他至少 E2。

### 7.2 变更分类与凭证路由

不同改动类别走不同门禁，避免"用大炮打蚊子"：

| 类别 | 典型改动 | 门禁 | 指纹绑定 | 证据 |
|---|---|---|---|---|
| 硬件/固件 | 代码、构建、配置、时序 | 硬件验收凭证 | 是 | receipt + 原始数据 |
| 主机/工具/测试 | 脚本、测试、hook | host 凭证 | 是 | pytest/用例 + receipt |
| 文档 | `.md`、索引、契约文本 | 文档门禁 | 否 | 检查器输出 |
| 未分类 | `.git`、`out/`、构建产物 | 不进门禁指纹 | — | 不适用 |

关键原则：**凭证必须绑定当前 staged 源码指纹**；文档改动不需要硬件凭证；工具/测试改动不需要台架。

### 7.3 凭证设计

一份合格凭证至少包含：

- schema 版本；
- scope（覆盖哪些路径/阶段）；
- 构建号/版本；
- 源码指纹/文件数；
- 执行命令与环境；
- 结果（PASS/FAIL/PARTIAL）；
- 未覆盖路径（unverified scope）；
- 恢复完整验收的条件（restore full condition）；
- 时间戳与失效条件。

凭证不是"通过"的同义词；`PASS_WITH_WARNINGS`、`PARTIAL` 必须如实记录。

### 7.4 验收流程

```text
固定范围 → 前置检查 → 执行 → 分级判定 → 生成 receipt →
独立复核 → 提交 → 索引/状态刷新
```

- **固定范围**：开始前写清 profile、必验阶段、质量目标；运行中新增观测不自动成为门禁。
- **前置检查**：版本、资源、许可、停机状态、校准状态。
- **分级判定**：INFO/WARN/ERROR/FATAL；分别输出阶段结果和总体结果。
- **独立复核**：复核者只读，检查 scope、指纹、原始数据、未覆盖路径。
- **提交**：代码/文档分离；提交信息带 build/指纹/凭证哈希或契约 ID。

### 7.5 失败处理

- 失败必须保留原始错误、返回值、状态快照、资源冲突、日志/波形。
- 不允许用"最终通过"摘要覆盖中间失败。
- 可恢复失败可以走**有界强制继续**，但必须记录次数、后继状态、终止条件；强制继续不改变失败事实。
- 不可恢复风险（越界、非法写入、失控输出）立即硬停，不做"再试一次"。
- 重试只用于幂等步骤；非幂等必须人工决策。

### 7.6 证据存储

```text
out/
  <task>/<run-id>/
    command.txt
    environment.json
    logs/
    raw/
    summary.json
    receipt.json
```

规则：

- 每次运行新目录，不覆盖旧失败。
- 证据目录只追加；需要压缩时冷热分层，不删除。
- 原始数据、日志、配置、哈希一起存。
- 证据包不含密钥/个人凭据。
- 证据路径写进进度日志和提交信息。

### 7.7 门禁接线

- 提交前自动路由：按改动类别选择 docs/host/firmware 门禁。
- 分类器失败时 fail-closed，不允许"分类不了就跳过"。
- hook 依赖本地配置（如 `core.hooksPath`）；clone/迁移后必须重配并验证。
- 允许逃生门，但必须写日志；每周审计绕过记录。
- 门禁脚本自身要有测试；门禁坏了等同于没有门禁。

### 7.8 常见失败模式

| 失败模式 | 后果 | 纠正 |
|---|---|---|
| 证据剧场 | 有 PASS 无 scope/指纹 | 凭证模板强制字段 |
| 旧证据复用 | 新 build 用旧凭证 | 指纹绑定 + 拒绝旧凭证 |
| 失败被摘要 | 问题被掩盖 | 原始失败单独字段 |
| 门禁太慢 | 大家绕过 | 拆分/缓存，≤5 秒 |
| 门禁误报 | 无关改动被拦 | 按类别路由，精确 scope |
| 只测 happy path | 边界失败 | 负例/故障注入 |

## 8. 多角色与多智能体协作

### 8.1 角色与决策权

| 角色 | 写权限 | 决策权 | 禁止 |
|---|---|---|---|
| 主控/项目负责人 | 全部（受门禁） | 范围、优先级、不可逆操作 | 自审自批 |
| 域 owner | 本域文件 | 本域语义/契约提案 | 改其他域 canonical |
| Worker | 指定文件集 | 无 | 越界写、改索引 |
| 独立复核者 | 只读 | 通过/驳回建议 | 改文件、操作设备 |
| 审计者 | 只读 | 审计结论 | 参与实施 |

关键：**写权限与决策权分离**；**作者与复核者分离**；**跨域索引只有一个写者**。

### 8.2 写域与车道

按改动类别划分车道，车道内文件集不相交：

| 车道 | 范围 | 门禁 |
|---|---|---|
| 文档 | `docs/**`、`*.md` | 文档门禁 |
| 固件/硬件 | 代码、构建、板级配置 | 硬件验收 |
| 工具/测试 | `tools/**`、`tests/**`、hooks | host 凭证 |
| 索引/契约 | 总索引、登记表、提交单索引 | 主控单写 + 文档门禁 |

并行工作的前提是**文件集不相交**。如果两个任务都要改同一个索引，必须串行或由主控统一写。

### 8.3 并行规则

1. 先拆分独立包，明确每个包的文件集和验收。
2. 独立包可以并行；有依赖的包串行。
3. 所有包完成后，合并 diff，交给**一个**独立复核者。
4. 复核者只读；发现问题回到对应包修正，不直接改。
5. 同一资源（设备/串口/构建目录）不允许并行写。
6. 共享索引由主控最后统一更新，避免"最后写者赢"。

### 8.4 交接包

给 worker/子 agent 的任务必须自包含：

```markdown
## 目标
- 要达成什么；不做什么。

## 上下文
- 必读文件（路径 + 为什么）。
- 当前状态/上轮结论。
- 已知约束/坑。

## 范围
- 允许修改的文件集。
- 只读文件集。
- 禁止操作（设备/提交/删除）。

## 验收
- 命令、期望输出、必须留下的证据。
- 失败时如何上报。

## 交付
- 改动摘要、证据路径、未决问题、下一步。
```

交接包不写"你自己看着办"；也不写长篇项目史，只给入口和边界。

### 8.5 独立复核

复核不是"再看一眼"，而是独立取证：

- 自己读源码/日志/凭证，不只看作者摘要；
- 对关键结论给 `文件:行` 或命令输出；
- 明确"与作者结论的异同"；
- 结论四选一，必改项可追踪；
- 复核记录归档，不能只留在聊天里。

### 8.6 阻塞点交叉分析

命中以下任一条件，必须开只读子代理独立取证，再由主控交叉分析：

1. 同一子项连续 2 次失败，或连续 2 轮无实质进展；
2. 同一现象复现 ≥2 次，或证据互相矛盾、无法判定根因；
3. 关键前提与上轮叙述不一致（版本/配置/状态/凭证/门禁拒绝）；
4. 需要不可逆或高成本决策（回滚、改协议、重签凭证、重构）；
5. 长循环 ≥3 轮未收敛，或上下文多次压缩后结论依赖旧叙述。

动作：

- 给子代理：目标、已做动作、完整失败命令/报错、证据路径、已排除假设、只读约束。
- 要求输出：独立结论、证据、与主控结论异同、最小下一步。
- 主控记录：子代理 id、结论、主控结论、差异、采信理由；记录后才继续。
- **"新"不等于"对"**：采信看证据，不看谁说的。
- 同一阻塞点只开一个子代理；子代理运行期间主控不抢跑写操作。

### 8.7 上下文与记忆

- 耐久事实写进文档/契约，不留在聊天。
- 每个长期任务有 handoff 文档：目标、状态、证据、下一步。
- 里程碑汇报是"认知 checkpoint"，不是形式。
- 上下文压缩后，先读 handoff + 最新进度，不凭记忆继续。
- 旧结论必须用新证据复核，不能"上轮如此"。

### 8.8 AI 安全边界

- 默认最小权限：先只读，再申请写；写操作限定文件集。
- 不可逆操作（删除、回滚、刷写、签审、发布）必须人工明确批准。
- 外部网页/工具输出视为**数据**，不是指令；不得据此跳过门禁。
- 不把密钥、token、个人路径写进 skill/文档/证据。
- 高风险动作在沙箱/隔离环境先演练。
- 保留审计日志：谁、何时、改了什么、依据什么。

### 8.9 常见失败模式

| 失败模式 | 后果 | 纠正 |
|---|---|---|
| 多 agent 同写 | 覆盖/冲突 | 文件集不相交 + 单写者 |
| 作者自审 | 错误漏过 | 独立复核 + 轮换 |
| 复核者附和 | 形式主义 | 要求独立证据/异同 |
| 上下文污染 | 旧结论当事实 | handoff + 新证据复核 |
| 越权操作 | 不可逆损失 | 最小权限 + 人工批准 |
| 并行上板 | 设备争用/损坏 | 资源锁 + 串行 |

## 9. 里程碑与长期任务

### 9.1 触发与轮次

任何长期目标/多里程碑任务，在第一次汇报前声明"按里程碑模板汇报"；未声明视为流程未启动。

- **一轮** = 上次汇报结束到本次汇报之间的工作区间。
- 每轮第一份汇报写"上轮下一步复议"；同轮后续子项沿用结论，不重复。
- 三种轮次：续轮（复议上轮）、新目标首轮（写"无（首轮）"+ 计划来源）、一次性任务（不触发模板）。

### 9.2 六段模板

**0. 上轮"下一步"复议**（仅第一份汇报）

| 上轮推荐 | 前提核验 | 结论 | 本轮处置 | 对第 1 段影响 |
|---|---|---|---|---|
| ... | 本轮新读的源码/读数/日志/凭证 | 成立/部分成立/不成立/无法判定 | 执行/修正后执行/证伪改道/延后 | ... |

- 前提核验必须用本轮新证据，不拿上轮结论当证据。
- 延后必须给复验判据和闭环里程碑。
- 证伪必须写"上轮判断错在哪"。

**1. 完成状态表**

| 子项 | 结果 | 改动类别 | 构建/指纹/文件 | 提交号 |
|---|---|---|---|---|
| ... | ✅/⏳/❌/⚠️ | feature/refactor/fix/tooling/docs | ... | ... |

- `⚠️` 仅限"已定位、已隔离、有复验判据"的残余。
- `pending`、未验证、延后不得写成 `✅`。

**2. 证据**

- host 用例、硬件/HIL 路径、凭证路径；必须可复跑。
- 写明 scope、构建、指纹、文件数、未覆盖路径。

**3. 质量门**

逐门给 `✅/⚠️/❌`，不空、不合并。通用门建议：

| 门 | 判定问句 |
|---|---|
| 契约 | 新增/变更的跨边界承诺是否登记并审核？ |
| 边界 | owner/写者/资源边界是否保持？ |
| 失败 | 失败路径是否 fail-closed，有 reason/证据？ |
| 版本 | 布局/协议/配置/凭证版本是否同步？ |
| 证据 | 凭证 scope 是否覆盖改动路径，能否复跑？ |
| 安全 | 是否触碰不可逆/安全红线？ |

**4. 偏差与残余**

- 偏差：`原计划 | 实际 | 理由 | 影响`。
- 残余：`# | 残余 | 状态(OPEN/MITIGATED/CLOSED) | 归属门 | 触发条件 | 影响面 | 复验判据 | 闭环里程碑`。
- 无偏差/无残余也要写"无"，不得留空。

**5. 提交与凭证**

- 代码/文档分离；提交信息带 build/指纹/凭证哈希或契约 ID。
- 说明哪些提交属于本轮，哪些是历史。

**6. 下一步**

- 下一子项、前置条件、是否被门禁阻塞。
- 未完成必须明确"仍 active"。
- 完成时给最终收口：子项总表、残余风险、契约状态、证据索引、提交清单。

### 9.3 硬规则

1. 第 0 段先行；缺失或只有复述 → 流程未启动。
2. 任一门禁 ❌ → 不进入下一子项。
3. `⚠️` 只用于已定位、已隔离、有复验判据的残余。
4. 上轮推荐的偏离必须显式记录。
5. 禁止"先做下一项，回头再补"。
6. 禁止用"基本可用/应该没问题"替代证据。
7. 阻塞点未解除不得标 ✅。
8. 最终收口必须给五件套（子项表、残余、契约状态、证据索引、提交清单）。

### 9.4 收口清单

- [ ] 所有子项有结果和证据；
- [ ] 所有 ❌/⚠️ 有归属、影响、复验判据；
- [ ] 契约状态与实际一致（pending 不冒充 active）；
- [ ] 证据路径可访问、可复跑；
- [ ] 提交已分离、信息完整；
- [ ] 索引/进度日志已更新；
- [ ] 下一阶段入口明确。

## 10. 落地路线图

### 10.1 最小可行治理（MVG）

如果只能做六件事，做这六件：

1. **一个总索引**：所有文档有入口，知道先读什么。
2. **一个三件套试点**：选一个域，跑通 Architecture/TODO/Task Progress。
3. **一个契约登记表**：只登记 3–5 条真正跨边界的承诺。
4. **一个门禁脚本**：元数据 + 索引 + 命名，提交前跑。
5. **一个工作流**：选一条多步、易失败的流程，做成可恢复 + 有 receipt。
6. **一个独立复核人**：不写代码，只读证据，每周一次。

这六件事能在 4–6 周内把团队从 L0/L1 拉到 L2。

### 10.2 分阶段路线

| 阶段 | 时间 | 目标 | 交付物 | 退出判据 |
|---|---|---|---|---|
| M0 基线 | 第 1 周 | 盘点与选点 | 文档清单、owner 表、试点域、风险清单 | 知道有什么、缺什么 |
| M1 文档与契约 | 第 2–4 周 | 事实可发现 | 索引、元数据、三件套、契约登记、进度日志、文档门禁 | 新文档 100% 过门禁 |
| M2 工具与工作流 | 第 2 月 | 执行可恢复 | 工具登记、判型、1 条 workflow、host 凭证、证据目录 | 试点流程可中断恢复 |
| M3 协作与评审 | 第 3 月 | 信任可审计 | 角色/写域、交叉审核、里程碑报告、阻塞分析 | 关键改动有独立复核 |
| M4 规模化 | 第 2 季度 | 体系自运转 | 度量、审计、培训、跨项目复用 | 门禁/评审不靠人盯 |

### 10.3 团队规模裁剪

| 规模 | 建议 | 可省略 |
|---|---|---|
| 1–2 人 | 索引 + 进度日志 + 一个门禁 + 一个 workflow | 正式契约表、复杂评审 |
| 3–5 人 | 三件套 + 契约表 + 工具登记 + 轮值复核 | 专职审计、复杂度量 |
| 10–50 人 | 分域、车道、判型、凭证路由、里程碑 | 全自动 L4 |
| 50+ | 域 owner、审计、度量、平台化 | 无（按需精简） |

### 10.4 结构工程领域适配

把通用概念映射到结构专业：

| 通用概念 | 结构专业落地 | 证据 |
|---|---|---|
| 文档三件套 | 设计说明/计算书；设计计划/专业条件；校审与修改记录 | 版本号、签审记录 |
| 契约 | 设计输入条件、荷载组合、计算假定、专业接口 | 条件表、会签单 |
| 工具 | 计算脚本、参数化建模、模型检查器、图纸比对 | 版本、运行日志、验证算例 |
| 工作流 | 方案→建模→分析→验算→出图→校对→审核→交付 | 模型哈希、计算书、校审单 |
| 凭证 | 计算书 + 模型 + 校审记录 + 专业会签 | 可复算包 |
| Skill | 规范检索、模型检查、审查意见提取、变更影响分析 | 触发词、检查清单 |

示例 AI 工作流（结构）：

```text
1. 读取项目索引、设计输入、专业条件（只读）
2. 生成"计算假定清单"草稿（AI 起草，工程师确认）
3. 调用版本化计算脚本（记录输入/版本/参数）
4. 对比结果与规范限值（自动检查 + 人工判断）
5. 生成校审包（模型、计算书、差异、未决项）
6. 校对/审核（人工门，AI 不签章）
7. 修改闭环（审查意见逐条回复，证据归档）
```

结构专业的三条红线：

1. **AI 不替代注册工程师签章**；安全相关计算必须有人复核。
2. **规范条文必须可追溯**（版本、条款号、适用条件），不能用 AI 记忆代替。
3. **模型/计算书/图纸三一致**；变更必须做影响分析，不能只改一处。

### 10.5 90 天启动计划

| 周 | 动作 | 产出 |
|---|---|---|
| 1 | 盘点文档/工具/流程；选试点；定 owner | 清单、试点、RACI |
| 2 | 建总索引 + 元数据模板 + 命名规则 | 索引、模板、规范 |
| 3 | 建三件套试点 + 契约登记表（3–5 条） | 试点文档、登记表 |
| 4 | 接文档门禁（元数据/索引/命名） | pre-commit 脚本 |
| 5–6 | 建工具登记 + 判型；选一条 workflow | 登记表、WorkflowSpec |
| 7–8 | 跑通 workflow 的恢复 + receipt；接 host 凭证 | 可中断恢复的流程 |
| 9–10 | 定角色/写域；做第一次独立复核 | 复核单、问题清单 |
| 11–12 | 第一次里程碑汇报；复盘；裁剪规则 | 报告、下一季计划 |

### 10.6 失败信号与止损

出现以下信号，说明治理过度或方向错了，应简化：

- 门禁 >10 秒，或经常拦无关改动；
- 登记表 80% 行长期不更新；
- 文档比代码长，但决策没增加；
- 每个任务都要 workflow，简单事也走重流程；
- 复核者开始"秒过"；
- AI 写、AI 审、AI 签；
- 团队开始普遍 `--no-verify`。

止损动作：砍掉低价值检查、合并登记表、缩短模板、把"必须"降为"建议"、每季度删一条规则。

## 11. 度量与审计

### 11.1 度量原则

- 少而准：5–8 个指标足够。
- 领先指标优先：能提前预警，而不是事后解释。
- 可行动：每个指标对应一个改进动作。
- 不度量"治理规模"：文档数、规则数、agent 数不是成绩。

### 11.2 指标表

| 类型 | 指标 | 口径 | 目标 |
|---|---|---|---|
| 领先 | 文档新鲜度 | 窗口内更新的 canonical 文档 / 应更新数 | ≥90% |
| 领先 | 契约覆盖率 | 已登记跨边界接口 / 应登记数 | ≥80% |
| 领先 | 首次门禁通过率 | 一次通过 / 总提交 | ≥70% |
| 领先 | 证据完整率 | 有关键凭证的改动 / 关键改动 | 100% |
| 领先 | 工作流恢复成功率 | 中断后成功恢复 / 中断次数 | ≥90% |
| 领先 | 未判型工具数 | 无判型行的工具族 | 0 |
| 滞后 | 返工率 | 复核后返工 / 总改动 | 下降 |
| 滞后 | 逃逸缺陷 | 交付后发现 / 总缺陷 | 下降 |
| 滞后 | 新人上手时间 | 到首次独立提交 | 下降 |
| 滞后 | 复现时间 | 找到并复跑历史结果 | 下降 |
| 反指标 | 文档字数/文件数 | — | 不设目标 |
| 反指标 | workflow/agent 数量 | — | 不设目标 |

### 11.3 审计节奏

| 频率 | 内容 | 产出 |
|---|---|---|
| 每周 15 分钟 | 门禁失败、逃生门、阻塞点 | 问题清单 |
| 每月 | 契约/工具/文档新鲜度、返工 | 月度健康报告 |
| 每季度 | 规则有效性、删除/合并、权限复核 | 治理简化提案 |
| 每半年 | 全量证据抽查、交接演练 | 审计报告 |

### 11.4 健康检查清单

- [ ] 新人能在 30 分钟内找到总索引和当前主线？
- [ ] 每个域有 owner 和入口 README？
- [ ] 文档元数据/索引/命名 100% 过门禁？
- [ ] 最近 3 个契约有独立审核记录？
- [ ] 所有跨边界接口都有契约或显式豁免？
- [ ] 新增工具都有判型行？
- [ ] 至少一条 workflow 能中断恢复？
- [ ] 关键改动有 receipt 且绑定指纹？
- [ ] 失败记录没有被"最终通过"覆盖？
- [ ] 逃生门有日志并每周审计？
- [ ] 复核者与作者不是同一人？
- [ ] 阻塞点有交叉分析记录？
- [ ] 里程碑报告六段齐全？
- [ ] `pending` 没有被写成 `active/✅`？
- [ ] 归档资料没有被当默认输入？
- [ ] 旧证据没有被用于新版本？
- [ ] 文档里的数字能追到源？
- [ ] 索引只有一个写者？
- [ ] 规则数量在下降或稳定，而不是膨胀？
- [ ] 团队没有普遍绕过门禁？

### 11.5 反模式清单

1. 文档倾倒场，无 owner、无索引。
2. 同一事实四处复制。
3. 快照当契约。
4. 契约只登记不验证。
5. 自审自批。
6. 门禁慢到被绕过。
7. 逃生门无记录。
8. 工具根目录堆脚本。
9. 双实现并存。
10. Skill 复制规则。
11. 万能 skill。
12. 一切都 workflow 化。
13. GUI 状态当唯一事实。
14. 失败后静默重跑。
15. 旧凭证用于新构建。
16. 证据只有截图没有原始数据。
17. 多 agent 同写一个文件。
18. 复核者只复述作者结论。
19. 用"上轮如此"代替证据。
20. 为了治理而治理。

## 附录 J：与 HDRT100 实现的映射

本规范抽象自 HDRT100 的文档自回归体系。下表只用于说明来源，**不是通用要求**；其他项目应保留概念，替换实现。

| 通用概念 | HDRT100 实现 | 迁移时保留什么 |
|---|---|---|
| 总索引 | `docs/README.md` | 单一入口 + 域路由 |
| 元数据 | 5 字段（Status/Domain/Canonical/Related/Last updated） | 机器可检、窗口固定 |
| 三件套 | Architecture / TODO / Task Progress | 语义/状态/证据分离 |
| 契约登记 | `DOCS_REGISTRY.md` | ID/锚点/状态/交叉审核 |
| 工具登记 | `tool_registry.json` | 身份/生命周期/依赖 |
| 判型 | `tool_workflow_triage.json` | 四型 + 迁移字段 |
| Skill | `.agents/skills/*/SKILL.md` | 触发 + 指针 + 命令 |
| 工作流 | `CONSOLE_WORKFLOW_ARCHITECTURE.md` | WorkflowSpec + 步骤模型 |
| 凭证 | `credential_scope.py` + receipts | 按改动类别分流 |
| 里程碑 | `DOCS_EXECUTION_CONSTRAINTS.md` §7 | 六段 + 硬规则 |
| 阻塞分析 | 只读子代理交叉分析 | 独立取证 + 采信记录 |

### 从 HDRT100 得到的五条经验

1. **验证不是走过场**：每轮自回归都能抓到真问题；检查器必须有正反用例。
2. **锚点必须以实际为准**：方案里的文件名常常是猜的，登记前先确认。
3. **门禁会静默失效**：hook 路径、最小 PATH、沙箱都会让门禁"看似通过"；迁移后必须重配并验证。
4. **数字最容易腐烂**：能引用符号就不要手写；快照必须标注。
5. **治理要能简化**：规则、债务、豁免都要有到期日和复审，否则体系会自我膨胀。

## 版本与维护

- 维护者：项目治理负责人（或指定 owner）。
- 复审周期：每季度一次；每次复审至少删除/合并一条低价值规则。
- 变更方式：提案 → 小范围试点 → 评审 → 发布；保留旧版本。
- 适用声明：本规范是通用方法，不替代具体项目的安全规范、法规和合同要求；结构专业的安全相关计算必须由具备相应资格的人员复核和签章。
