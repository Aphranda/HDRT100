## 0. 这份指南怎么用

这是 [通用规范](STANDARDS_PROJECT_MANAGEMENT_SYSTEM_ARCHITECTURE.md) 的**采用手册**，不是第二份标准。它回答：

- 一个外部团队 90 天内怎么开始；
- 先做什么、后做什么；
- 哪些门禁必须保留、哪些可以裁剪；
- 什么情况下应该停止，而不是继续加规则。

原则：**不要照抄全文，先复制最小闭环，再按项目裁剪。**

## 1. 采用原则

1. **先立事实源，再上工具**：没有索引和 canonical，工具越多越乱。
2. **一次只改一个系统**：先文档/索引/门禁，再契约、工具、工作流。
3. **先只读，再写入**：AI 默认只读；写操作限定文件集。
4. **先 host/离线，再台架**：能用 host 测试证明的，不占硬件资源。
5. **证据先于叙述**：没有命令、数据和路径的“完成”不算完成。
6. **模板可裁剪，门禁不可口头**：可以少做，但不能假装做了。
7. **每个阶段有退出判据**：没有判据的阶段会无限延长。
8. **治理要能删减**：每季度至少删掉/合并一条低价值规则。

## 2. 90 天采用路线

| 阶段 | 时间 | 目标 | 关键产物 | 退出判据 |
|---|---|---|---|---|
| A 基线 | 第 1–2 周 | 知道有什么、谁负责、先改哪里 | 文档/工具/流程清单、owner 表、试点、成功指标 | 试点和 owner 明确 |
| B 事实源 | 第 3–4 周 | 文档可发现、可检查 | 总索引、元数据模板、命名规则、一个三件套、文档门禁 | 新文档 100% 过门禁 |
| C 契约与工具 | 第 5–6 周 | 跨边界承诺和工具身份可追踪 | 3–5 条契约、工具登记/判型、进度日志 | 契约有锚点，工具无未判型新增 |
| D 一条工作流 | 第 7–8 周 | 多步流程可恢复、有证据 | 1 条 WorkflowSpec、state 文件、receipt、host 测试 | 中断后能恢复；失败有证据 |
| E 独立复核 | 第 9–10 周 | 有人能独立判断“完成” | 交叉审核单、里程碑报告、残余清单 | 关键改动有非作者复核 |
| F 规模化 | 第 11–12 周 | 决定是否推广 | 指标、复盘、裁剪清单、下一季目标 | 通过/修改/停止的明确结论 |

时间可按团队规模压缩，但**顺序不要跳**：没有 A/B 直接上 D，工作流会变成新的脚本堆。

## 3. 角色与职责

| 角色 | 职责 | 不该做什么 |
|---|---|---|
| 赞助人 | 提供授权、资源和跨团队协调 | 不直接改技术文件 |
| 项目负责人 | 定范围、优先级、退出判据 | 不给自己发验收合格证 |
| 域 owner | 维护本域语义、契约提案、TODO | 不改其他域 canonical |
| AI 工作流负责人 | Skill、工具、Workflow、证据链 | 不让 AI 自审自批 |
| 独立复核者 | 只读取证、复核证据和结论 | 不改文件、不操作设备 |
| 一线使用者 | 按流程执行、反馈可用性 | 不绕过门禁“先跑起来” |

最小配置：项目负责人 + 一个域 owner + 一个独立复核者。  
1–2 人团队可以轮值复核，但不能作者自审。

## 4. 最小产物清单

| 产物 | 完成判据 | 可裁剪 |
|---|---|---|
| 项目入口文档（AGENTS/章程） | 权威顺序、车道、门禁命令写清 | 不可裁剪 |
| 总索引 | 每个受治文档有入口 | 不可裁剪 |
| 文档模板 | 5 字段元数据 + 命名规则 | 不可裁剪 |
| 一个三件套 | Architecture/TODO/Task Progress 分工明确 | 首月可只做一个域 |
| 契约登记表 | 3–5 条跨边界契约，ID/锚点/状态齐全 | 小团队可延后 |
| 工具登记/判型 | 新增工具先判型；关键工具有 owner | 小团队可只登记 Top-10 |
| 一条 WorkflowSpec | 有 state、resume、receipt | 首月可只做一条 |
| 证据目录 | 每次运行独立目录，不覆盖失败 | 不可裁剪 |
| 里程碑报告 | 0–6 段模板，能回答“下一步” | 可简化，但不能只有“完成了” |

## 5. 门禁与凭证

| 门禁 | 触发 | 判据 | 是否需要台架 |
|---|---|---|---|
| 文档门禁 | 改 `.md` | 元数据/索引/命名/链接/新鲜度 | 否 |
| 契约门禁 | 登记/改状态 | ID 唯一、锚点真实、交叉审核 | 否 |
| 工具门禁 | 新增/改工具 | 判型、登记、依赖/布局 | 否 |
| 工作流门禁 | 新增/改 workflow | Spec 字段、resume、receipt | 否（host） |
| host 凭证 | 改工具/测试 | 测试通过 + 指纹绑定 | 否 |
| 硬件凭证 | 改固件/构建/硬件行为 | P3/HIL 凭证 + scope | **是** |

关键规则：**凭证按改动类别分流，不按项目阶段分流。**  
文档/工具/测试改动不要占台架；固件/硬件行为改动不能只用 host 测试结案。

## 6. 第一周做什么

1. 指定项目负责人和第一个试点域。
2. 列出现有文档、脚本、手工流程、验收证据。
3. 找出“同一个事实有多个版本”的 3 个例子。
4. 建总索引，只登记现有入口，不追求一次收全。
5. 选一条最痛、最重复的多步流程作为试点。
6. 约定成功指标：找事实时间、返工次数、证据可复跑率。
7. 明确“本周不做什么”：不搞全量迁移、不引入新平台、不追求自动化。

## 7. 按团队规模裁剪

| 规模 | 保留 | 可以延后/省略 |
|---|---|---|
| 1–2 人 | 索引、进度日志、一个门禁、一条 workflow | 正式契约表、复杂评审、专职审计 |
| 3–5 人 | 三件套、契约表、工具登记、轮值复核 | 专职审计、复杂度量 |
| 10–50 人 | 分域、车道、判型、凭证路由、里程碑 | 全自动 L4 |
| 50+ | 域 owner、审计、度量、平台化 | 无（但每季度精简） |

## 8. 结构工程示例

| 通用概念 | 结构专业落地 | 证据 |
|---|---|---|
| 文档三件套 | 设计说明/计算书；设计计划/专业条件；校审与修改记录 | 版本号、签审记录 |
| 契约 | 设计输入、荷载组合、计算假定、专业接口 | 条件表、会签单 |
| 工具 | 计算脚本、参数化建模、模型检查器、图纸比对 | 版本、运行日志、验证算例 |
| 工作流 | 方案→建模→分析→验算→出图→校对→审核→交付 | 模型哈希、计算书、校审单 |
| 凭证 | 计算书 + 模型 + 校审记录 + 专业会签 | 可复算包 |

一条最小工作流：

```text
读取设计输入 → 生成计算假定清单（AI 起草，工程师确认）→
调用版本化计算脚本 → 对比规范限值 → 生成校审包 →
人工校对/审核 → 修改闭环 → 归档
```

红线：AI 不替代注册工程师签章；规范条文可追溯；模型/计算书/图纸三一致。

## 9. 止损信号

出现以下情况，暂停推广，先收缩：

- 门禁超过 10 秒，或经常拦无关改动；
- 文档比代码长，但决策没有增加；
- 工具登记 80% 行长期不更新；
- 所有任务都被要求走 workflow；
- 复核者开始“秒过”；
- AI 写、AI 审、AI 签；
- 团队普遍 `--no-verify`。

止损动作：砍检查、合登记表、缩模板、把“必须”降为“建议”、每季度删一条规则。

## 10. 90 天检查清单

- [ ] 有项目负责人和试点域；
- [ ] 有总索引和 5 字段元数据模板；
- [ ] 有一个域的三件套；
- [ ] 有 3–5 条契约，ID/锚点/状态齐全；
- [ ] 新增工具都有判型；
- [ ] 有一条可恢复的 workflow；
- [ ] 关键改动有 host 或硬件凭证；
- [ ] 有一次独立复核；
- [ ] 有一份里程碑报告；
- [ ] 有明确指标和下一季目标；
- [ ] 明确哪些规则被裁剪；
- [ ] 没有把“未验证”写成“完成”。

## 11. 采用后的下一步

- 第 2 季度：把一条主线做到 L3（证据可复跑），不要全量铺开。
- 第 3 季度：引入季度复审和规则删减。
- 第 4 季度：评估是否扩展到第二个域/第二个项目。

需要把本指南落到具体项目时，使用配套的本地化工具包：`STANDARDS_LOCALIZATION_KIT_PLAYBOOK.md`。
