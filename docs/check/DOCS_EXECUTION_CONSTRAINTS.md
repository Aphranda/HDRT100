4. 与历史快照、旧任务消息或已废止流程冲突时，以当前 canonical 文档和最新用户指令为准，并保留冲突证据。

## 2. 工具、编码与工作区

### EXE-TOOL-01：统一可复核的项目命令

- 项目命令优先使用工作区约定的 Git Bash：`D:\Aphranda\Git\bin\bash.exe`。
- 如果某个工具只能在 PowerShell、CMD 或 Python 原生环境运行，可以使用等效入口，但必须在报告中说明原因和实际命令。
- Markdown、Python、配置和源文件按 UTF-8 读取；修改使用 `apply_patch`，不得覆盖或回滚未授权的用户改动。
- 构建、测试、验收、波形、时序和审计中间产物统一写入 `out/` 的任务子目录。临时 pytest basetemp 也必须位于 `out/`，根目录不得留下 `.tmp-*` 或同类临时目录。

### EXE-TOOL-02：事实源与快照边界

- 硬数字、状态结论和能力声明必须回到代码符号、登记表或原始验收证据。
- 无法绑定事实源的数字必须标注“快照，非事实源”，不能在本文固化为产品事实。
- 当前 OTA 块大小、某次 build/HIL 编号、debug 配额、worker 数量和单轮完成结论属于任务快照，不应直接迁入本文。

### EXE-CODE-01：.c/.h 文件行数预算

- 新文件（`components/*/src/*.c` 等）：≤800 行；拆分后的单元 ≤1,500 行。
- 现有 >2,000 行的文件：必须登记 TODO/拆分计划；>3,000 行冻结新功能（拆分/修复除外）。
- 聚合器/SCPI 文件：单文件 ≤1,300 行。
- 拆分约束：纯移动/重命名 + 私有头；不改行为；每步 build + P3 + HIL/SCPI 烟测；代码/文档分离。
- 当前超标文件（2026-10-25 快照，非事实源）：`distributed_refmem.c` 5,763、`scpi_system_snapshot_commands.c` 5,712、`vdc_dpll_manager.c` 4,826 等；由 N5.0 拆分目标收口。
- 行数预算目前**没有**机器检查器（原计划的 c 文件预算检查脚本未实现），超标以
  评审发现并在域 TODO 登记，不假装有门禁。

### EXE-TOOL-03：脚本进场须先做 workflow 归型

用户要求（2026-11-04）：tools 的约束按 workflow 定义执行——**任何在用的脚本都要先判型，新增脚本先判型再使用**。

- 归型唯一事实源：`tools/tool_workflow_triage.json`（schema `TOOLS_WORKFLOW_TRIAGE_V1`），四种形态：
  - `WORKFLOW`：分阶段编排，必须声明入口、`out/` 证据根、续跑方式；**并满足
    `docs/console/CONSOLE_WORKFLOW_ARCHITECTURE.md` 的 WorkflowSpec**（id/version、inputs、preconditions、
    steps、transport、receipt_schema）与步骤模型；不满足的不得标 WORKFLOW，应按 STEP/STANDALONE 归型并登记迁移；
  - `STEP`：由某个 WORKFLOW 调用，必须用 `workflow` 指向该 WORKFLOW；
  - `STANDALONE`：单次命令、单一目的；
  - `LIBRARY`：被 import 复用，不得声明入口。
- 机检：`python tools/tool_governance/workflow_triage.py check --quiet`（挂在 pre-commit 的 host 分支）。
  `*_workflow.py` 入口未判 WORKFLOW、非 `UNASSESSED` 家族没有归型行、WORKFLOW 缺证据根/续跑方式
  → FAIL；`UNASSESSED` 家族未判 → WARN（存量债务：把生命周期升级到 EXPERIMENTAL 之前必须补判）。
- 判型是**使用前置条件**：新增脚本默认按 workflow 形式设计，没有归型行不得进入 `tool_registry.json` 的
  EXPERIMENTAL 及以上；确实不需要 workflow 的，必须在 `reason` 说明为什么（单次命令/无阶段/无恢复/无凭证）。
- 现存脚本**逐步迁移**：判型行用 `target_form` + `milestone` 登记目标形态与里程碑，检查器输出
  `migration pending` 警告；迁移完成后把 `form` 改成目标形态并删除这两个字段。禁止「先用起来再补」。
- 归型是治理声明：改 `form`、新增 WORKFLOW、或把家族升级生命周期，同批提交并在提交信息说明理由。

## 3. 变更与证据闭环

### EXE-CHANGE-01：独立改动的最小交付单元

每个独立代码、PIO、构建、工具或测试改动必须按以下顺序完成：

1. 明确状态机节点、变更边界、风险和回滚方式。
2. 运行相关软件测试并记录完整命令和结果。
3. 编译受影响配置，保留 build 输出和源码指纹。
4. 对**固件/构建**改动执行硬件验收；分类以 `tools/acceptance/credential_scope.py` 为准——
   工具、测试、hook 与文档走各自的 host/docs 凭证，不需要台架。验收凭证必须绑定当前 staged 源码指纹。
   常规迭代使用 `python tools/hardware_acceptance/workflow_steps.py dpll60`
   （证书 schema `HAOFV_HARDWARE_ACCEPTANCE_RECEIPT_DPLL60_V1`，scope `DPLL60_JOINT`）：
   复用已成功的 package/OTA，经一次有限 TDMA 阶段应用已冻结校准矩阵并给出四板 STOP 原始交接，
   再执行四板 DPLL 60 s 联合观测。该证书**不能覆盖**校准测定、P1–P3 延迟试验及其严格质量门、
   CLK/DATA 训练测定、存储/SD、sync I/O、flash/OTA 健壮性与外部示波器路径——这些正是
   `DPLL_SHORT_UNCOVERED_PREFIXES` 列出的路径；staged 改动命中其中任一路径（含 OTA 工具）时，
   `check-staged` 拒绝该证书，必须回到完整验收 `workflow_steps.py run`。
   证书自带的 `unverified_scope` 与 `restore_full_condition` 字段是这条范围声明的机器可读副本。
   完整验收 `python tools/hardware_acceptance/workflow_steps.py run` 共有 **37 个步骤函数**，可
   `--run <dir>` 续跑；`--reuse-flashed`（用户要求 2026-11-02）在没有固件改动、四板已跑同一 build 时
   跳过构建与刷写，直接进校准/TDMA/DPLL，只有源码指纹变化才重新构建刷写。
5. 将成功、失败、拒绝原因、资源冲突、状态快照和原始数据写入 `out/`。
6. 主控复核证据后，代码与文档分离提交；提交后按任务授权选择性 push。

失败不能被摘要覆盖。`forced_continue` 只能表示调试流程在记录拒绝后继续，不得写成严格门禁通过。

### EXE-SEAT-01：特等席增设须用户审核

用户要求（2026-09-19）：新增或扩容 DPLL/VDC/SYNC 特等席位，必须先取得用户明确审核同意，再实施。既有主线授权不等于授权增加席位。审核材料须列出载荷语义、owner、字节数、频率、Core1 最坏耗时、当前占用及剩余预算，并说明对既有席位及后续 SYNC 的影响；未测余量必须标为待验证，不能按空闲字节直接授予实时能力。

VDC 健康镜像、统计和查询属于异步诊断，不新增特等邮箱、快速通道处理或 Core1 发布工作。由 Core0 有界读取既有快照，允许延后；镜像的 FRESH/age 是采样时状态，不能作为实时控制或锁相授权。实现变更同时检查 wire 席位与 CPU/IRQ 静态预算，不借 GUARD 或其他域配额。

本条记录任务执行授权边界，不新增 wire 契约；产品资源变更仍按原登记与交叉审核流程处理。

### EXE-STATE-01：状态机迁移与 TDMA 短帧闭环

- 每次状态机状态或状态边界发生改动后，必须先完成 TDMA 短帧闭环，再进入下一项迁移。
- 闭环失败时，使用 SD 波形/逻辑分析工具定位，保留原始波形、解析结果和修复前后对比；未修复不得推进。
- 旧 build、不同源码指纹或仅有 host 测试的闭环证据不能证明当前切片已验收。
- 短帧闭环至少应能回溯目标 build、板卡/链路、周期或帧计数、`passed`、`closed_loop_passed`、实时门禁结果、诊断结果、强制继续标记和原始证据目录。

### EXE-OTA-01：OTA 时序失败处理

- OTA 传输完成、设备状态发布、端口关闭、复位、USB 重枚举和提交确认必须分别记录时间和原始响应。
- `IDLE`、`PermissionError`、重枚举失败或 post-reset race 必须保留为失败证据；不得只增大 timeout 或改变最终状态判断来掩盖时序问题。
- OTA 工具改动必须先有 host/仿真回归，再进行新固件硬件验收；硬件仍运行旧 build 时，不得用旧证据替代新 build 验收。

## 4. Debug 安全门禁

### EXE-ACCEPT-01：固定验收范围与阶段信息分级

验收开始前固定 profile、必验阶段和严格质量目标，写入 `fixed-scope.json`。
调试中新增观测不自动成为当前切片门禁。规则实现以
`tools/hardware_acceptance/p3_alarm_policy.py` 和主脚本 `acceptance_scope()` 为准；
以下为执行规则，不新增固件或跨域产品契约。

| 级别 | 判定与处理 |
|---|---|
| INFO | 正常信息、未选候选、预期拒绝、可选项目跳过；保留记录，不阻断。 |
| WARN | 已有可用参数或基本运输，但存在重复性、连续性、调度或锁相质量问题；允许完成快速验收。 |
| ERROR | 本轮必验目标、必要身份/配置/有效运输或证据完整性未满足；不能签发本轮通过凭证。普通执行异常归此类，不能仅凭错误文字推定不可恢复风险。 |
| FATAL | 有明确结构化证据的不可恢复风险；按 EXE-SAFE-02 停止相关运行。普通 PIO stall 或相关候选失败不自动归此类。 |

| 阶段 | 基础目标 | 候选与质量信息 |
|---|---|---|
| P0/P0T | 完整所需环序、身份与编号对应正确，清理完成；兼容的已确认线序可复用。P0T 的功能是从物理活动中识别唯一线序；未校准前帧可能偶然对齐，也可能完全不对齐，因此 frame/magic 命中只作诊断，唯一线序已成立时不得据其失败。 | 其他候选链路不通为 INFO，不要求全连接；STOP ACK 仍须结合新鲜状态读回确认，不能因兼容成功文本误报失败。 |
| P1 | 后继可用的 CLK 粗捕获输入。 | 搜索窗口外拒绝为 INFO；粗测质量不足但后继已验证所选输入可用为 WARN。 |
| P2 | 后继可用的编码 marker 时间基线。 | 未选相关候选失败为 INFO；已选输入可用但重复质量不足为 WARN。 |
| P3 | 指定稳定工作档位、链路和信号组的有效延迟基线。 | 明确标为非必验 LIMITED_RX 且高于目标稳定频率的探测试验失败为 INFO；目标档位失败仍阻断。 |
| T0/TRN-00 | MARK 与驻留时间输入可用。 | 未选 offset 失败为 INFO；选中参数已装载验证但测量质量不足为 WARN。 |
| T1/TRN-01 | SCK offset 输入可用。 | 未选候选失败为 INFO；窗口裕量/重复性不足独立告警。 |
| T2/TRN-02 | DATA 窗口输入可用。 | 窗口外候选拒绝为 INFO；已选窗口质量不足独立告警。 |
| T3/TRN-03 | 所需板卡实际完成选中矩阵装载、identity/各 link 读回；不以矩阵文件 passed 替代硬件装载。 | 新训练未通过但已选兼容参数实际装载可用为 WARN，不能宣称重新测量通过。 |
| TDMA | 所需节点实际收到有效新数据，TX/RX 序号推进，有限采集的 STOP 与原生记录交接有效。 | 偶发缺帧、启动稳定窗口失败、反馈超窗和相位迟到为 WARN；持续无有效输入、缺节点、STOP/证据无效为 ERROR。 |
| DPLL | 按本轮选定目标验证参考/控制/锁相；未执行为 SKIPPED。 | DCO 零调整不等于故障；未锁与精度不足在普通调试中告警，显式锁相专项才阻断。 |

阶段 PASS、PASS_WITH_WARNINGS、FAIL、SKIPPED 与总体验收结果分别输出。
快速模式沿用固定基础范围；`--strict-stage` 显式将指定阶段质量列入本轮必验，
不能运行后自动增加。严格模式沿用完整质量要求。
原始 `passed`、`strict_gates_passed` 和失败记录保留，分级报告不改写旧失败。
新凭证绑定 `alarms.json`、判定输入、固定范围与原始阶段文件，并复算分级；
数据缺失、混用旧原件或仅修改告警标签不能放行。

### EXE-SAFE-01：可恢复拒绝的记录与有界继续

Debug profile 下，可恢复的门禁拒绝、资源冲突、状态不稳定、校准失败或诊断失败必须记录：

- 拒绝原因和原始返回值；
- 资源冲突和参与者；
- 状态快照、计数器和时间戳；
- 原始串口、波形、日志或存储数据；
- 有界强制继续次数、后继状态和终止条件。

记录后可沿有界强制继续路径推进，直到下一状态、超时或本轮结束。强制继续不改变失败事实，也不提升为产品模式行为。

调试阶段的控制参数例外：DPLL/环路滤波器调参命令可以接受任意可解析的有符号或
无符号参数，包括零、负系数和超出产品建议范围的限值。调试接口不得用数值范围
检查代替证据；必须保留原始 SCPI、requested/applied generation、active profile
CRC、状态/residual/frequency/reject 读回和回退结果。固件实时算术仍须饱和并防止
整数溢出，参数更新只能经过 owner mailbox 和确定性 service boundary；格式错误、
邮箱覆盖、资源冲突或不可恢复硬件风险仍可拒绝并记录。接受异常参数不代表接受
`LOCKED`、`FORMAL_LOCKED` 或产品 RUN。

DPLL 失锁和 DPLL phase 的局部 WCET/deadline 超限属于调试反馈；只要 TDMA
UP/DOWN、process-image、FIFO 和基础收发仍连续，不能因此新增实时负载隔离或屏蔽
节点。调参器应使用这些反馈小步调整并等待后续样本收敛，节点级隔离只适用于 TDMA
或不可恢复硬件资源故障。

### EXE-SAFE-02：不可恢复风险硬停

仅下列不可恢复安全风险允许硬停：越界 DMA、非法内存或 Flash 操作、失控 GPIO，以及经代码/硬件证据确认等价的不可逆风险。产品 profile 继续保持严格拒绝。

## 5. Worker 与主控职责

### EXE-ROLE-01：worker 边界

- 文档 worker 先只读审计，按 A/B/C/D 输出逐文件问题、证据、建议动作、批次和契约登记影响；未经确认不得修改文档、检查器或 `.agents/`。
- 状态机 worker 聚焦一个明确状态或切片；不得跨越 TDMA 短帧闭环、编译、软件/硬件验收和证据复核直接进入下一状态。
- worker 不得把旧约束、旧设备映射、旧 build 或旧验收报告当作当前事实；发现时效性冲突必须上报。

### EXE-ROLE-02：主控复核

主控负责核对源码差异、测试覆盖、build 指纹、TDMA/SD 原始证据、硬件验收凭证和远端状态。只有证据闭合后才选择性 commit/push；遇到外部阻塞必须保留原始失败并明确下一可执行动作。

## 6. 文档自回归与契约边界

- 新增或修改 `docs/**` 文档语料必须满足 5 字段元数据、命名规则、`docs/README.md` 索引和 `Last updated` 要求。
- `.agents/skills/**` 下的 skill、配套说明与评审文本采用独立格式，具体范围及 Git 跟踪、独立评审要求见 `AGENTS.md` §2「文档格式范围」。该格式例外不改变安全、授权、契约和 EXE-CHANGE-01 实现验收义务，也不取消仓库级规则或文档治理实现变更的文档门禁。
- 文档门禁使用 `tools/docs_check/docs_check.py --strict-names`、`tools/doc_regression_check.py`、对应 pytest 和 pre-commit；所有临时输出放入 `out/doc-audit/<run-id>/`。
- 本文是流程规范草案，不新增 `DOCS_REGISTRY` 契约。若将其中某条冻结为产品或跨域运行时契约，必须下沉到对应域 canonical，登记唯一 `contract_id`，并按 C11 交叉审核和顶层刷新规则处理。
- 契约登记行不可物理删除，只能转为 `superseded`；评审快照和草稿不得登记为契约。

## 7. 长期目标里程碑汇报（EXE-REPORT-01 正文）

> 本节是里程碑汇报的**唯一正文**：0–6 段模板、硬规则与阻塞点交叉分析都在这里。
> `AGENTS.md` §8 只保留触发条件与红线，禁止再放第四份副本。

### 7.1 触发、轮次与声明

- **触发**：任何长期目标/多里程碑任务（N3.x/N4.x 等）的第一次汇报前，必须声明“本次按 §8 模板汇报”；未声明视为流程未启动。
- **一轮** = 上一次 §8 汇报结束到本次汇报之间的工作区间。每轮**第一份**汇报写第 0 段；同轮后续子项沿用其结论，不重复第 0 段。
- **三种轮次，第 0 段写法不同**：
  1. **续轮**（同一目标）：逐条复议上轮第 6 段“下一步”，不得跳过。
  2. **新目标首轮**：第 0 段写“无（首轮）”+ 本轮计划来源；不重做上轮，但第 4 段必须列出继承残余。
  3. **非目标一次性任务**：不触发本文 §7；一旦按目标轮汇报，就必须完整套用。
- 第 0 段缺失、只有复述没有前提核验、或用上轮结论充当证据 → 本轮流程未启动，不得开新改动、不得把任何子项或目标标成完成。

### 7.2 汇报模板（0–6 段）

**0. 上轮“下一步”研讨（仅第一份汇报）**

表格列：`上轮推荐 | 前提核验 | 结论 | 本轮处置 | 对第 1 段影响`。

- 前提核验：必须用本轮新读的源码/读数/日志/凭证复核，不拿上轮结论当证据。
- 结论四选一：`成立 / 部分成立 / 不成立 / 无法判定`。
- 处置四选一：`执行 / 修正后执行 / 证伪改道 / 延后`；与结论对应；延后须给复验判据与闭环里程碑。
- 已闭环项也要写“已完成 + 证据”，不能省略；上轮建议缺项/含糊时按残余处理，不得当作已闭环。
- 证伪必须写“上轮判断错在哪”。
- 新目标首轮：写“无（首轮）”+ 计划来源，不得编造上轮建议。

**1. 完成状态表**

列：`子项 | 结果 | 改动类别 | P3 build/fingerprint/files | 提交号`。

- 结果只用 `✅/⏳/❌/⚠️`；`⚠️` 仅限“已定位、已隔离、有复验判据”的残余。
- 类别按 `AGENTS.md` §2.7 凭证分流：`feature / refactor / fix / tooling / docs`。

**2. 证据**

- host 用例、四板 HIL 路径、P3 凭证路径；路径必须可复跑。
- 凭证必须写明 scope（如 `FULL` / `QUICK_DIAGNOSTIC`）、build、源码指纹、文件数、未覆盖路径。

**3. HAOFV 六门 + C1/C2**

逐门给 `✅/⚠️/❌`，不空、不合并；每门必须正面回答判定问句。C1/C2 单独结论，任一不成立即 `❌`，不得记 `⚠️`。

- ① 无新增总线/payload class/第二命令槽/第二 ACK 事实（新增载荷是否已登记白名单、回程是否仍唯一？）
- ② 不占 core1 硬实时窗口或拉长一等席周期（phase/seat/静态预算是否用工具或符号重新核算？新增/扩容席位是否有 EXE-SEAT-01 用户审核？）
- ③ 单写者/owner 边界保持（状态实例数是否仍为 1；phase 归属、RUN 只读 active、component→service→SDK 方向是否未变？）
- ④ 故障 fail-closed + reason/evidence（每条失败路径是否有 reason、计数、快照；F0–F3 分级是否仍成立？）
- ⑤ 布局/版本/契约同步（DeploymentGate 的 build/app map/hw/config/cal/sync CRC 是否同步；错误码是否在本域段且未复用冻结枚举？）
- ⑥ host + 四板证据可复跑（凭证 scope 是否覆盖改动路径；host/build/runtime/HIL/hardware 五层是否按需给出？）
- **C1 Flash/XIP**：erase/program 仍只由 core0 发起，core1 park ACK 有效，临界区内无 XIP/USB/SD/LCD 访问。
- **C2 时间事实**：raw tick 未被回写，时间差使用 `int32_t` 回绕安全写法，换代重基与同代回退判据未混淆。

**4. 偏差与残余**

分两小节，禁止混写。

- **偏差**：本轮对上轮建议或本轮计划的偏离（修正后执行/证伪改道/延后/改步骤/换凭证）。写 `原计划 | 实际 | 理由 | 影响`；第 0 段已写的上轮偏离可引用，不重复展开。
- **残余**：表 `# | 残余 | 状态 | 归属门 | 触发条件 | 影响面 | 复验判据 | 闭环里程碑`。
  - 状态三选一：`OPEN`（未闭环）/ `MITIGATED`（已缓解仍继承）/ `CLOSED`（有证据关闭）。
  - `OPEN`/`MITIGATED` 必须写全五字段；缺项按 `❌`。
  - `CLOSED` 必须给证据（commit/凭证/路径）；只需一行，不再重复分析。
  - 无偏差/无残余也要写“无”，不得留空；延后必须用户明确接受，记为**非完成项**。
- **直接 `❌`，不得降级为 `⚠️`**：
  - 触碰 C1 或 C2；
  - refactor 出现同名状态跨 TU 双实例、`#if`/`#include` 边界被切开、段/RAM_TEXT 归属未核算、初始化顺序依赖未声明；
  - RUN 态写 active 配置，或绕过 STOP/ARM 边界激活；
  - 用旧 build、旧源码指纹或 scope 不覆盖的凭证充当本轮证据；
  - 命中 `docs/arch/ARCH_REALTIME_LOAD_MOUNTING_CONSTRAINTS.md` §6 任一越界判定。

**5. 提交与凭证**

- 代码/工具与文档分离；代码提交前 `check-staged` 按 staged 指纹核验 P3；文档提交前跑 `AGENTS.md` §5 全部门禁。
- 提交信息带 build/fingerprint/凭证 sha，或契约变更的 `contract_id`。

**6. 下一步**

- 下一子项、前置条件、是否被门禁阻塞；未完成必须明确“仍 active”。
- 完成时必须给最终收口：子项总表、未完成/残余风险、契约状态、证据索引、提交清单，并明确目标是否可标记完成。

### 7.3 硬规则（违反即流程未启动/`❌`）

- **第 0 段先行**：缺失、只有复述没有前提核验、或用上轮结论充当证据 → 不得开新改动、不得标完成。
- **硬件验收工作流每次失败必须开子代理交叉分析**：任何 `hardware_acceptance_workflow.py` / `workflow_steps.py` 步骤失败，同时起只读子代理独立取证（给失败步骤、报错、产物路径，要求证据行号与独立结论）；主会话再交叉分析、记录异同后才允许继续改动。
- **上轮推荐的偏离必须显式**：修正后执行 / 证伪改道 / 延后都要记录理由；延后项按第 4 段规则记为非完成项。
- **任一门禁 `❌`/未通过 → 不进入下一子项**，先归因修正；`⚠️` 只用于“已定位、已隔离、有复验判据”的残余，且必须写偏差、影响、闭环里程碑。
- **refactor 等价性**：拆分/迁移/重命名另须给状态实例数、导出符号集、条件编译组合、段/RAM_TEXT 归属、host 同集全绿，必要时给 map diff；缺任一项按未验证处理。
- `pending` 契约、未验证项、延后项不得写成 `✅` 或“完成”。
- 禁止“先做下一项，回头再补”，禁止用“基本可用/应该没问题”替代证据。
- **长期任务阻塞点强制交叉分析**：命中 7.4 任一条件时，未完成只读子代理取证、主会话对照差异并记录采信理由，不得继续改动/上板，也不得把该阻塞点写成完成。
- 最终收口必须给：子项总表、未完成/残余风险、契约状态、证据索引、提交清单，并明确目标是否可标记完成。

### 7.4 阻塞点交叉分析（长期任务防判断衰减）

**目的**：长期任务跨多轮、多次上下文压缩后，容易复用旧结论、漏掉前提变化，或把“上轮如此”当成证据。阻塞点必须由主会话与只读子代理各自取证，再做**交叉分析**，不能由单方结论直接推进。

**定义**：交叉分析 = 主会话与只读子代理**各自独立取证**，再对照结论与证据差异，由主会话记录采信理由后裁决；不是“主会话提问、子代理附和”，也不是“子代理单独给结论就直接执行”。

**设计意图**：新开子代理没有本会话的历史结论和上下文包袱，可提供低确认偏差的第二视角；但它也缺少项目上下文，必须给它目标、约束和证据路径，并要求独立读源码/日志。**“新”不等于“对”**：采信仍以证据和交叉差异为准，不以“子代理说了”或“主会话先前如此”为准。

**判定（任一即阻塞点）**：

1. 同一子项连续 **2 次失败**，或连续 **2 轮无实质进展**；
2. 同一现象复现 **≥2 次**，或证据互相矛盾、现有日志无法判定根因；
3. 关键前提与上轮叙述不一致：build/源码指纹/config/板状态/凭证/门禁拒绝；
4. 需要不可逆或高成本决策：factory reflash、回滚、改协议/布局、重签凭证；
5. 长循环 **≥3 轮**未收敛，或上下文已多次压缩且结论依赖旧叙述。

**动作**：

- 在继续改动/上板前，开一个**只读子代理**；给它：目标与当前里程碑、已做动作、完整失败命令/报错、证据路径（日志/凭证/状态 JSON）、已排除假设、只读约束。
- 要求输出：独立结论、证据（`文件:行`/DIAG 字段/命令输出/产物路径）、与主会话结论的异同、最小下一步；禁止只复述主会话叙述，禁止改文件/上板。
- 主会话必须交叉分析并记录：子代理 id、子代理结论、主会话结论、差异、采信理由；记录后才允许继续/改道/停。
- 同一阻塞点只开一个子代理；子代理运行期间主会话可做只读取证，但不得抢跑写代码或操作硬件。
- 阻塞点未解除不得标 `✅`；按第 4 段记 `OPEN`/`MITIGATED`，并写复验判据与闭环里程碑。
- 子代理不可用/超时：记录原因和主会话已做的独立取证，按“未交叉分析”残余处理，不得静默跳过。
- **分析与执行分离**：子代理只分析；写操作/硬件操作仍由主会话在交叉分析后执行。

> 本条的覆盖范围比 7.3“硬件验收工作流步骤失败”更广：硬件失败仍强制子代理；长期任务的其他阻塞点也按本条执行。
